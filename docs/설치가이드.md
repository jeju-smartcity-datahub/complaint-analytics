# 설치·실행 매뉴얼

제주 데이터허브 민원 분석 서비스를 로컬에서 띄우는 방법을 설명한다.

| 구성 요소 | 디렉터리 | 기술 | 포트 |
| --- | --- | --- | --- |
| DB | `database/` | PostgreSQL 15 + PostGIS 3.4 | 25433 |
| 백엔드 | `repos/backend/` | Java 17 · Spring Boot 3.5 · 전자정부표준프레임워크 5.0 | 8070 (Docker) / 8180 (로컬) |
| 배치 | `repos/batch/` | Java 17 · Spring Boot 3.5 · Spring Batch 5 | 8280 |
| 프론트 | `repos/frontend/` | React 18 · Vite 5 · TypeScript | 8080 via nginx (Docker) / 5173 (로컬) |

실행 방법은 두 가지다.

- **[방법 A] Docker로 전체 실행**: 화면까지 한 번에 띄워 본다. 보통은 이쪽을 쓴다.
- **[방법 B] 소스에서 직접 실행**: 코드를 고치면서 개발한다.

두 방법 모두 **DB를 먼저 띄운다**.

---

## 0. 사전 준비

| 항목 | 방법 A | 방법 B |
| --- | --- | --- |
| Docker (Compose v2) | 필수 | 필수 (DB용) |
| Java 17 | – | 필수 (Gradle toolchain이 17을 요구) |
| Node.js 20 이상 | – | 필수 |
| 인터넷 | 필수 | 필수 |

인터넷은 두 곳에 필요하다.

- 빌드 때 Maven Central과 전자정부 저장소 `maven.egovframe.go.kr`에서 의존성을 받는다.
- 실행 때 OIDC IdP에 접속한다.

**OIDC 클라이언트 자격증명**(`client-id`, `client-secret`)이 필요하다. 없으면 백엔드가 기동하지 않는다. IdP에는 로그인 후 돌아올 주소를 redirect URI로 등록해 둔다.

- 방법 A: `http://localhost:8080`
- 방법 B: `http://localhost:5173`

> Apple Silicon(arm64): `postgis/postgis:15-3.4` 이미지는 amd64만 있어서 에뮬레이션으로 돈다. 동작은 정상이다.

## 1. DB 기동 (공통)

```bash
cd database
cp .env.example .env      # 비워 두면 기본값: jeju / jeju1234 / jeju_datahub / 포트 25433
docker compose up -d
docker compose logs -f db # "[init] 완료" 가 보이면 끝 (Ctrl+C)
```

데이터 볼륨이 비어 있으면, 첫 기동 때 `database/init/20-load-ddl.sh`가 아래 순서로 자동 적재한다.

1. `ddl/jeju-datahub-schema.sql`: `parking` 스키마 38개 테이블, `batch` 스키마 15개 테이블, 함수, PostGIS 확장
2. `ddl/load-data.sql`: `ddl/data/*.csv` 기준데이터 11개 테이블

### 적재 확인

```bash
docker exec jeju-datahub-db psql -U jeju -d jeju_datahub -Atc "
  select 'tb_menu', count(*) from parking.tb_menu
  union all select 'tb_grid', count(*) from parking.tb_grid
  union all select 'tb_btch_schdl', count(*) from batch.tb_btch_schdl"
# tb_menu|18
# tb_grid|229522
# tb_btch_schdl|8
```

기준데이터만 들어 있고 민원·단속 같은 업무 데이터는 없다. 그래서 대시보드와 분석 화면은 빈 결과로 나온다. 업무 데이터는 배치 잡으로 수집한다([4장](#4-배치-잡-수동-실행)).

### 초기화 다시 하기

자동 적재는 **데이터 볼륨이 비어 있을 때만** 돈다. 처음부터 다시 적재하려면 볼륨을 지운다.

```bash
docker compose down -v
docker compose up -d
```

### 수동 적재

이미 있는 PostgreSQL + PostGIS 서버에 적재할 때 쓴다. `load-data.sql`이 상대경로를 쓰므로 반드시 `ddl/` 안에서 실행한다.

```bash
cd database/ddl
psql -h <호스트> -p <포트> -U <계정> -d <DB> -v ON_ERROR_STOP=1 -f jeju-datahub-schema.sql
psql -h <호스트> -p <포트> -U <계정> -d <DB> -v ON_ERROR_STOP=1 -f load-data.sql
```

## 2. [방법 A] Docker로 전체 실행

루트 `docker-compose.yml`은 백엔드, 배치, 프론트, nginx를 띄운다. DB는 포함하지 않으므로 1장에서 띄운 DB에 접속한다.

```
브라우저 ─▶ nginx(:8080) ─┬─ /      ─▶ frontend:3000
                          └─ /api/  ─▶ backend:8070 ─▶ DB (host.docker.internal:25433)
batch:8280 ─▶ DB,   backend ⇄ batch (서비스 간 API 키)
```

### 2-1. 환경변수 준비

```bash
# 저장소 루트에서
cp .env.example .env
```

`.env`에서 **필수 4개**를 채운다. 다른 IdP를 쓰면 `OIDC_ISSUER_URI`도 함께 바꾼다.

| 변수 | 값 |
| --- | --- |
| `OIDC_CLIENT_ID` | IdP에서 발급받은 client-id. 비어 있으면 백엔드 기동 실패 |
| `OIDC_CLIENT_SECRET` | IdP에서 발급받은 client-secret |
| `INTERNAL_API_KEY` | 임의 문자열. 배치가 백엔드를 호출할 때 쓴다 |
| `BATCH_API_KEY` | 임의 문자열. 백엔드가 배치를 호출할 때 쓴다 |

두 API 키는 `openssl rand -hex 32` 같은 명령으로 만든다.

> ⚠️ `.env`에서 값 뒤에 주석을 붙이지 않는다. `KEY=   # 설명`이라고 쓰면 `# 설명`이 값으로 들어간다.

DB 계정이나 포트를 바꿨다면 `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USERNAME`, `DB_PASSWORD`도 `database/.env`와 같게 맞춘다. 나머지 변수는 [5장](#5-환경변수-정리)을 본다.

### 2-2. 기동

```bash
docker compose up -d --build   # 처음 빌드는 수 분 걸린다
docker compose ps              # backend, batch, frontend 가 healthy 인지 확인
```

브라우저에서 **http://localhost:8080** 을 열고 로그인한다.

### 2-3. 동작 확인

```bash
curl -s -o /dev/null -w '%{http_code}\n' localhost:8080/              # 200 (화면)
curl -s -o /dev/null -w '%{http_code}\n' localhost:8080/api/auth/me   # 401 (로그인 전이면 정상)
curl -s localhost:8080/api/auth/authorize-url                         # authorizeUrl 에 client_id·redirect_uri 가 들어 있어야 한다
docker compose exec backend curl -s localhost:8070/actuator/health    # {"status":"UP"}
docker compose exec batch   curl -s localhost:8280/actuator/health    # {"status":"UP"}
```

### 2-4. 중지

```bash
docker compose down            # 앱 중지 (DB 는 database/ 에서 따로 관리)
```

## 3. [방법 B] 소스에서 직접 실행

터미널 3개에서 각각 띄운다. 이 방식에서는 백엔드와 배치가 **`local` 프로파일**로 뜬다.

> 🔴 `local` 프로파일은 DB 주소가 `localhost:25432`로 고정돼 있다. 반면 `database/docker-compose.yml`의 기본 포트는 25433이다. 아래 둘 중 하나로 맞춘다.
> - 아래 예시처럼 `SPRING_DATASOURCE_URL` 환경변수로 덮어쓴다.
> - `database/.env`에 `POSTGRES_PORT=25432`를 넣고 DB를 띄운다. 이 경우 방법 A의 `.env`에서도 `DB_PORT=25432`로 맞춘다.

> 백엔드와 배치는 `.env` 파일을 자동으로 읽지 않는다. 셸에서 `export`하거나 IDE 실행 설정(Run Configuration)의 환경변수에 넣는다.

### 3-1. 백엔드 (포트 8180)

```bash
cd repos/backend
export SPRING_DATASOURCE_URL='jdbc:postgresql://localhost:25433/jeju_datahub?currentSchema=parking,public'
export OIDC_ISSUER_URI=https://manager.project.dtonic.io:10443
export OIDC_CLIENT_ID=<client-id>
export OIDC_CLIENT_SECRET=<client-secret>
./gradlew bootRun
```

- 헬스체크: `curl -s localhost:8180/actuator/health` 결과가 `{"status":"UP"}`
- Swagger UI: http://localhost:8180/swagger-ui.html
- `currentSchema`에서 `public`을 빼면 안 된다. PostGIS 함수가 `public`에 있다.

여러 값을 파일로 관리하려면 셸에서 한 번에 export한다.

```bash
set -a; source ./my-backend.env; set +a
./gradlew bootRun
```

### 3-2. 배치 (포트 8280)

```bash
cd repos/batch
export SPRING_DATASOURCE_URL='jdbc:postgresql://localhost:25433/jeju_datahub?currentSchema=parking,public'
# 개발 중에는 스케줄 자동 실행을 끈다
export COMPLAINT_SYNC_SCHEDULED=false PBLPKLT_SYNC_SCHEDULED=false RISKNOTI_SYNC_SCHEDULED=false \
       UTZTN_SYNC_SCHEDULED=false SFTYCHCK_SYNC_SCHEDULED=false ZONENM_SYNC_SCHEDULED=false \
       RPTP_SYNC_SCHEDULED=false ACDNT_SYNC_SCHEDULED=false
./gradlew bootRun
```

- 헬스체크: `curl -s localhost:8280/actuator/health` 결과가 `{"status":"UP"}`
- `local` 프로파일은 API 키 인증이 꺼져 있다. 그래서 키 없이 `curl localhost:8280/api/batch/ops/jobs`로 잡 목록을 볼 수 있다.
- 부팅만 해서는 잡이 실행되지 않는다(`spring.batch.job.enabled=false`).

### 3-3. 프론트 (포트 5173)

```bash
cd repos/frontend
npm ci
npm run dev
```

http://localhost:5173 을 연다. `/api` 요청은 Vite 프록시가 `http://localhost:8180`(3-1의 백엔드)으로 보낸다.

배경지도에 VWorld 키가 필요하면 `repos/frontend/.env.local`에 `VITE_VWORLD_API_KEY=<키>`를 넣는다.

### 3-4. 빌드와 테스트

```bash
(cd repos/backend  && ./gradlew build)    # 컴파일 + 테스트 + jar
(cd repos/batch    && ./gradlew build)
(cd repos/frontend && npm run build)      # 타입체크 + vite build → dist/
```

## 4. 배치 잡 수동 실행

잡을 실행하려면 원천 자격증명이 필요하다. 이 값이 없으면 잡이 명확한 오류로 실패한다. 기동 자체는 이 값 없이도 된다.

- D-Hub: `DHUB_USER_EMAIL`, `DHUB_USER_PW`
- 지오코딩: `VWORLD_API_KEY`

| 잡 | 트리거 |
| --- | --- |
| `complaintFetchJob` (민원 수집) | `POST /api/batch/complaint-fetch` |
| `crackdownFetchJob` (단속 수집) | `POST /api/batch/crackdown-fetch` |
| `pblpkltFetchJob` (공영주차장 수집) | `POST /api/batch/pblpklt-fetch` |
| `riskAlertJudgeJob` (위험단계 판정) | `POST /api/batch/risk-alert-judge` |

전체 잡 목록과 파라미터는 잡 카탈로그 `GET /api/batch/ops/jobs`에서 확인한다.

```bash
# 방법 B (local, 키 불필요)
curl -X POST localhost:8280/api/batch/complaint-fetch

# 방법 A (배치 포트는 호스트에 열려 있지 않다 → 컨테이너 안에서 호출)
docker compose exec batch sh -c 'curl -X POST -H "X-API-Key: $BATCH_API_KEY" localhost:8280/api/batch/complaint-fetch'
```

관리자 권한으로 로그인하면 운영 화면 `/ops/batch`에서도 실행하고 스케줄을 바꿀 수 있다.

### 스케줄 자동 실행

자동 실행 여부는 두 단계로 정해진다.

1. 환경변수 스위치: 방법 A에서는 `BATCH_SCHEDULED`. 기본값은 `false`이고, `false`면 해당 잡은 등록되지 않는다.
2. 스케줄 표 `batch.tb_btch_schdl`의 `use_yn`과 `cron_expr`. 운영 화면에서 바꾸면 재기동 없이 반영된다.

`crackdownFetchJob`(단속 수집)은 1번 스위치가 없어 스케줄 표 값만 따른다. 그래서 원천 자격증명 없이 자동 실행되지 않도록 기준데이터에 `use_yn=N`으로 넣어 두었다. `pkltAcdntFetchJob`(사고이력 수집)도 초기값이 `N`이다. 두 잡을 자동 실행하려면 운영 화면에서 켠다.

배치 기동 로그에서 등록 상태를 확인한다. `use_yn=N`이면 환경변수 스위치와 관계없이 `disabled`로 표시된다.

```
[schedule] disabled job=...   ← 스케줄 표 use_yn=N
[schedule] blocked  job=...   ← 환경변수 스위치로 꺼짐
[schedule] registered job=... ← 자동 실행 등록됨
```

## 5. 환경변수 정리

방법 A의 루트 `.env` 기준이다. 방법 B에서는 같은 이름을 셸이나 IDE에 export한다. 단, DB는 `SPRING_DATASOURCE_*` 변수를 쓴다.

### 필수

| 변수 | 쓰는 곳 | 설명 |
| --- | --- | --- |
| `OIDC_CLIENT_ID` / `OIDC_CLIENT_SECRET` | 백엔드 | OIDC 클라이언트 자격증명. ID가 비어 있으면 기동 실패 |
| `INTERNAL_API_KEY` | 백엔드·배치 | 배치가 백엔드 내부 API를 호출할 때 쓰는 키. 비어 있으면 503 |
| `BATCH_API_KEY` | 백엔드·배치 | 백엔드가 배치 API를 호출할 때 쓰는 키. 비어 있으면 503 |

### 접속과 인증

| 변수 | 기본값 | 설명 |
| --- | --- | --- |
| `WEB_PORT` | `8080` | 브라우저 접속 포트 |
| `DB_HOST` / `DB_PORT` | `host.docker.internal` / `25433` | 컨테이너에서 접속할 DB 주소 |
| `DB_NAME` / `DB_USERNAME` / `DB_PASSWORD` | `jeju_datahub` / `jeju` / `jeju1234` | `database/.env`와 같게 맞춘다 |
| `OIDC_ISSUER_URI` | `https://manager.project.dtonic.io:10443` | IdP 주소. 소스 실행(방법 B)의 기본값은 예시 주소 `https://idp.example.com` 이므로 실제 주소를 export 한다 |
| `OIDC_REDIRECT_URI` | `http://localhost:8080` | IdP에 등록한 값과 글자 하나까지 같아야 한다(끝 슬래시 주의) |
| `FRONT_BASE_URL` | `http://localhost:8080` | 로그인 후 돌아갈 프론트 주소 |
| `SESSION_COOKIE_SECURE` | `false` | http 접속이면 `false`, https면 `true`. http에서 `true`면 로그인이 유지되지 않는다 |

### 선택

| 변수 | 설명 |
| --- | --- |
| `DHUB_USER_EMAIL` / `DHUB_USER_PW` / `DHUB_BASE_URL` | 배치 원천(D-Hub) 자격증명. 잡 실행 시 필요 |
| `BATCH_SCHEDULED` | `true`면 스케줄 표에 따라 잡이 자동 실행된다(기본 `false`) |
| `VWORLD_API_KEY` / `VWORLD_BASE_URL` | 서버 측 지오코딩(백엔드·배치) |
| `VITE_VWORLD_API_KEY` / `VITE_VWORLD_BASE_URL` | 프론트 배경지도. 브라우저에 그대로 노출되므로 공개 키만 넣는다 |
| `AGENT_API_BASE_URL` / `AGENT_ID` | AI 어시스턴트 연동 |

### 방법 B 전용

| 변수 | 설명 |
| --- | --- |
| `SPRING_DATASOURCE_URL` / `_USERNAME` / `_PASSWORD` | `local` 프로파일의 고정 DB 주소(`localhost:25432`, jeju/jeju1234)를 덮어쓴다 |
| `*_SYNC_SCHEDULED` | 배치 잡별 스케줄 스위치(`COMPLAINT_`, `PBLPKLT_`, `RISKNOTI_`, `UTZTN_`, `SFTYCHCK_`, `ZONENM_`, `RPTP_`, `ACDNT_`) |

## 6. 문제 해결

| 증상 | 원인 | 해결 |
| --- | --- | --- |
| 백엔드 기동 실패: `Client id of registration 'dhub2' must not be empty` | `OIDC_CLIENT_ID`가 비어 있다 | 값을 넣는다 |
| 백엔드·배치 기동 실패: `Connection refused` | DB가 안 떠 있거나 포트가 다르다 | 1장의 DB를 먼저 띄우고 포트를 확인한다. 방법 B는 3장의 25432/25433 안내를 본다 |
| 로그인 후 바로 다시 로그인 화면으로 돌아온다 | http 접속인데 세션 쿠키가 `secure`다 | `SESSION_COOKIE_SECURE=false` |
| IdP가 `redirect_uri` 불일치 오류를 낸다 | 등록값과 `OIDC_REDIRECT_URI`가 다르다 | 끝 슬래시와 포트까지 글자 그대로 맞춘다 |
| 운영 화면이나 배치 연동 API가 503 | `INTERNAL_API_KEY` 또는 `BATCH_API_KEY`가 비어 있다 | 두 키를 채우고 `docker compose up -d`로 다시 띄운다 |
| 대시보드가 비어 있다 | 업무 데이터(민원·단속)가 없다 | 정상이다. 4장의 배치로 수집한다 |
| DB를 다시 띄워도 DDL이 적재되지 않는다 | 자동 적재는 빈 볼륨일 때만 돈다 | `docker compose down -v` 후 재기동 |
| `jeju-datahub-db` 컨테이너 이름 충돌 | 같은 이름의 컨테이너가 이미 있다 | 기존 컨테이너를 정리하거나 `database/docker-compose.yml`의 `container_name`을 바꾼다 |
| 집중구역·공간 분석이 SQL 오류를 낸다 | `currentSchema`에 `public`이 빠졌다 | `currentSchema=parking,public`을 유지한다 |
